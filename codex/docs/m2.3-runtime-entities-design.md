# M2.3 — Runtime entities

**Status:** draft for review  
**Date:** 2026-10-05  
**Scope:** define the domain runtime model needed by the in-memory store,
scheduler, agent and future transport layer.

## Goals

- Add typed `Job`, `Agent` and `Allocation` values without mixing user input
  (`JobSpec`) with runtime state.
- Represent identifiers, statuses, timestamps, terminal results, availability
  and attempt metadata explicitly.
- Keep domain types independent of HTTP, persistence and OS process APIs.
- Provide response snapshots and typed lifecycle event payloads for the future
  versioned transport.

## Data model

Each entity lives in its own domain module: `job.rs`, `agent.rs` and
`allocation.rs`. `timestamp.rs` owns `Timestamp`; `dto.rs` owns snapshots; and
`event.rs` owns lifecycle event payloads. Fields remain private; read-only
accessors expose stable values. Initial constructors create only the normal
initial state. Lifecycle mutation is deferred to M2.6's single transition
policy. HTTP request DTOs are defined with the later transport endpoints.

### Timestamp

Add `Timestamp`, a `u64` newtype containing Unix epoch milliseconds. It exposes
`from_unix_millis` and `as_unix_millis`; Serde uses an integer. The domain does
not read the system clock. Callers supply timestamps, which keeps tests
deterministic and allows the application layer to inject its clock. No time
crate is added.

### Job

`Job` contains:

- `JobId` and the existing `JobSpec`;
- `JobStatus`: `pending`, `assigned`, `running`, `succeeded`, `failed`,
  `stopped` or `lost`;
- `submitted_at`, `updated_at`, optional `started_at` and optional `finished_at`;
- optional `TerminalResult`.

`Job::new(id, spec, submitted_at)` starts in `pending`; `updated_at` equals
`submitted_at`, and start/finish/result values are absent. `TerminalResult` is
one of `Exited { exit_code }`, `SpawnFailed`, `Stopped` or `Lost`. The lifecycle
policy maps `Exited { exit_code: 0 }` to succeeded, non-zero exit codes and
`SpawnFailed` to failed, and the remaining results to their matching terminal
statuses. Results contain no arbitrary process or environment text.

### Agent

`Agent` contains `AgentId`, an opaque address string, `last_heartbeat_at`,
`AgentHealth` (`healthy`/`unhealthy`) and `AgentAvailability` (`idle`/`busy`).
The address stays a string so parsing and validation remain at the transport
boundary. `Agent::new(id, address, registered_at)` initializes a healthy, idle
agent with `last_heartbeat_at = registered_at`.

### Allocation

`Allocation` contains `AllocationId`, `JobId`, `AgentId`, `AllocationStatus`, a
non-zero `attempt` number, and `assigned_at`, optional `started_at` and optional
`finished_at`. Its constructor starts in `assigned`. The first attempt is 1;
MVP does not retry, but the explicit number identifies the execution attempt
without relying on insertion order.

`AllocationStatus` is `assigned`, `running`, `succeeded`, `failed`, `stopped`
or `lost`. The allowed transitions and consistency rules between job and
allocation results are not implemented in this task.

`Allocation::new(id, job_id, agent_id, attempt, assigned_at)` takes
`attempt: NonZeroU32`, so zero cannot be represented.

## Snapshots and lifecycle events

Status, result and reason enums serialize using snake_case values. Runtime
entities are not deserialized from external payloads. `JobSnapshot`,
`AgentSnapshot` and `AllocationSnapshot` are separate Serialize-only response
DTOs. `JobSnapshot` contains the fields `id`, `spec`, `status`, `submitted_at`,
`updated_at`, `started_at`, `finished_at` and `terminal_result`.
`AgentSnapshot` contains `id`, `address`, `last_heartbeat_at`, `health` and
`availability`. `AllocationSnapshot` contains `id`, `job_id`, `agent_id`,
`status`, `attempt`, `assigned_at`, `started_at` and `finished_at`. Conversions
are `From<&Job> for JobSnapshot`, `From<&Agent> for AgentSnapshot` and
`From<&Allocation> for AllocationSnapshot`. HTTP request DTOs are defined with
their transport endpoints in later tasks.

Add a tagged, serializable and deserializable `JobEvent` enum. The JSON `type`
discriminator uses snake_case variant names. All timestamps use `Timestamp`.
The event field layout is:

| Variant | Required fields |
| --- | --- |
| `submitted` | `job_id`, `occurred_at` |
| `assigned` | `job_id`, `allocation_id`, `agent_id`, `occurred_at` |
| `started` | `job_id`, `allocation_id`, `agent_id`, `occurred_at` |
| `finished` | `job_id`, `allocation_id`, `agent_id`, `occurred_at`, `result: ProcessResult` |
| `stopped` | `job_id`, optional `allocation_id` and `agent_id`, `occurred_at`, `reason: user_requested` |
| `lost` | `job_id`, `allocation_id`, `agent_id`, `occurred_at`, `reason: heartbeat_expired` |

`ProcessResult` is `Exited { exit_code }` or `SpawnFailed`. The tagged `type`
discriminator applies to `JobEvent`; nested result/reason values are snake_case
enum values. `StopReason` currently has `UserRequested`; `LostReason` currently
has `HeartbeatExpired`. In a stopped event the allocation and agent IDs are
either both present or both absent. Assignment and execution events use the
assigned IDs. These types describe payload shape; M2.4 finalizes status meanings,
terminal classification and event requirements.

`occurred_at` is a `Timestamp`. Assignment and execution events carry both
allocation and agent IDs. A stop may omit them because a pending job can stop
before assignment. A lost event always identifies the allocation and agent.

The event type records facts; it does not apply transitions or decide whether a
duplicate or stale event is acceptable. M2.4 owns terminal-state and event
semantics; M2.6 owns transition enforcement.

## Error and state behavior

- Constructors require explicit IDs, values and timestamps; the domain does not
  generate time implicitly.
- `Allocation::new` requires a positive attempt number (`NonZeroU32`); zero is
  unrepresentable in the constructor API.
- Runtime entities are not accepted directly as external input; only the
  dedicated DTOs and event payloads define their wire representation.
- State-transition validation, stale/duplicate event handling and terminal
  status consistency are deferred to their roadmap tasks.

## Consequences

- The model adds no dependency and performs no async or I/O work.
- Unix-millisecond timestamps are compact and deterministic; the v1 API uses
  this numeric representation unless a later protocol decision changes it.
- The address string is intentionally opaque at the domain layer; transport
  registration validates its syntax before constructing an `Agent`.
- `AgentHealth`, availability and allocation state are explicit snapshots. The
  application/liveness policy updates them consistently.

## Acceptance checks

- Each entity can be constructed in its documented initial state.
- Serde round-trips snapshots and every event variant with IDs, states,
  timestamps, result and reason.
- Attempt metadata is positive by type and survives snapshot serialization.
- Domain tests use fixed values and do not read a clock or start a process.
